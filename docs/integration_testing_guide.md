# 5.4 Integration Test(s)

Integration testing is needed for this project because the system is a pipeline made of multiple cooperating modules, not a single isolated program. GeeksforGeeks defines integration testing as testing combined units after unit testing so that interface defects can be found. That applies directly to this project because success depends on the handoff between scripts and runtime environments: YouTube links must become audio files, audio files must be correctly numbered, the numbering must stay consistent with the URL index, and the diarization job must read those files and produce transcript outputs. A unit test can confirm that one helper function works, but it cannot prove that the outputs of one module are valid inputs for the next module.

For this reason, the project should use an incremental integration strategy. The most practical approach is to automate the local file-based part of the pipeline and describe the cluster-dependent part as a manual integration procedure. A fully automated end-to-end test for every backend is not necessary for this assignment because the final stage depends on external factors such as SLURM scheduling, GPU availability, Hugging Face model access, Python environment installation, and network access for downloading packages or media. Those dependencies make a full-stack automated test expensive and brittle. However, the interfaces between the project’s own modules still need to be verified.

The automated integration test added for this project is in `tests/test_integration_pipeline.py`. This test combines `audio_numbering.py` and `youtube_audio_batch.py` in one workflow. The test starts with one existing unnumbered audio file in `audio_in/` and one YouTube URL in a temporary links file. First, it runs the numbering script and verifies that the existing file becomes `001_...`. Next, it runs the YouTube batch script with the actual file-system behavior but a mocked download function, so the test stays fast and deterministic. The test then verifies that the newly downloaded audio file is renamed to `002_...`, the URL-to-audio index file is updated, the resolved-audio list is written, and the recorded metadata matches the downloaded item. This confirms that the boundary between numbering, downloading, renaming, and indexing works correctly.

The second integration test for the project should be a manual end-to-end procedure. First, run `scheduler/run_youtube_audio_download.sbatch` and verify that the job logs are created, the resolved audio paths all point inside `audio_in/`, and the downloaded files are numbered consistently. Second, run `scheduler/submit_bulk_diarization_job.sh --backend nemo` or `--backend pyannote` and confirm that each numbered audio file produces both a `.txt` transcript and a `.srt` subtitle file in the job output directory. Also verify that `runtime_summary.tsv` lists every processed audio file and that no output path escapes the expected folders. This manual test is appropriate because the assignment explicitly allows manual integration testing and because the diarization stage depends on cluster resources and third-party models.

In summary, integration testing is needed for this project because the main risk is not only whether each script works by itself, but whether the scripts work together as one system. What is *not* necessary is a fully automated cluster-wide end-to-end test for every backend and model combination. For this assignment, one automated integration test for the project-owned pipeline logic plus one documented manual full-system procedure is the correct balance.
